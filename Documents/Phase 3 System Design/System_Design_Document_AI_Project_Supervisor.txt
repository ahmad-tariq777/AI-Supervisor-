04. System Workflow Document

4.1 Purpose and Scope

This document describes the step-by-step workflows of the AI Project Supervisor module for every user role and for each of its
five components. It translates the requirements of the Software Requirements Specification (Sections 02 and 03) into operational
flows: who performs each action, how the system and the AI Supervisor respond, which business rules are enforced, and what output
each workflow produces.

The workflows cover the Student, Team Leader, Team Member, Supervisor, Super Admin, Sub Admin and AI Supervisor roles. How the AI
performs its work is specified in Section 05, and how the system is built is specified in Section 06.

4.2 Conventions

Table 1: Actor abbreviations and conventions

  ---------------------------------------------------------------------------------------------------------------------------------
  Term                      Meaning
  ------------------------- -------------------------------------------------------------------------------------------------------
  S                         Student (a registered student account).

  TL                        Team Leader: a student who coordinates a team-based project. The project creator is the initial Team
                            Leader.

  TM                        Team Member: a student who joined a team by accepting an invitation.

  SV                        Supervisor: a human academic or project supervisor.

  SA / SB                   Super Admin / Sub Admin.

  AI                        AI Supervisor: an automated system role, not a human account. It acts only through the AI services,
                            within the permissions of the requesting user.

  SYS                       The platform backend (Node.js and Express API, database and background jobs).

  Project-level roles       Team Leader and Team Member are roles held within a project. A user keeps one account-level role (for
                            example Student) and gains a project-level role through team membership.

  Status names              Task, verification and priority names are written exactly as defined in the SRS.

Actors: Any user (registration is for students).

Preconditions: None.

Outcome: An authenticated session carrying the user identity and role.

Rules enforced: Every user must have an authenticated account and an assigned role; deactivated accounts cannot access protected
functionality (SRS 3.4, 3.5).

  ----------------------------------------------------------------------------------------------------------------------------------
  Step     Actor           Action                                              System / AI response
  -------- --------------- --------------------------------------------------- -----------------------------------------------------
  1        User            Opens the registration page and submits name,       SYS validates the input, checks that the email is
                           email, password and required profile details.       unique, stores a hashed password and assigns the
                                                                               default Student role.

  2        User            Logs in with email and password.                    SYS verifies the credentials, rejects deactivated
                                                                               accounts and issues a signed session token that
                                                                               carries identity and role.

  3        SYS             Routes the user after login.                        The user lands on the dashboard for the account role:
                                                                               student dashboard, supervisor dashboard, Super Admin
                                                                               console or Sub Admin console.

  Role assignment. Registration creates Student accounts. The Super Admin assigns the Supervisor role and promotes users to Sub
  Admin (SRS 3.5). The first Super Admin account is created when the platform is installed (seeded by the deployment procedure).

                           are approved.

05. AI Functionality Specification

5.1 Purpose and Scope

This section specifies the intelligent functionality of the AI Project Supervisor: what the AI is responsible for, how the locally
hosted language model is run through Ollama, how Llama 3.2 3B is used, which machine learning models are built with Python and
Scikit-learn, how Retrieval-Augmented Generation (RAG) grounds research answers, what data is needed to train and operate these
parts, and what the limitations are and how the design handles them.

Where the SRS fixes a choice (Ollama, Llama 3.2 3B, Python with Scikit-learn, LangChain or LlamaIndex) the choice is stated as a
requirement. Where the SRS leaves a detail open (for example the exact ML algorithms, the embedding model or the vector store)
this section gives a proposed design and marks it as proposed.

Design principles. The following principles guide every AI feature.

-   Local and private. The language model runs on the platform host through Ollama; project data is not sent to a hosted model
    service.

-   Language model for language, code for exactness. Llama 3.2 3B writes, explains and reasons in text. Dates, percentages,
    dependency checks, status changes and permissions are computed by deterministic code and never left to the model.

-   Structured and validated output. Every AI result is requested in a fixed schema, validated, and rejected if invalid.

-   Grounded research. Research answers are produced only after RAG retrieval and carry the references of the retrieved sources.

-   Recommendations, not decisions. AI results are recommendations. Humans approve baselines, plans and completion, and a
    supervisor can override verification results with a recorded reason.

-   Traceable. Every AI recommendation and verification decision is recorded with enough detail to be reviewed.

5.5.2 Prompt Design Rules

-   Each call has one task and a short system prompt that states the role, the allowed output schema and the rules (for example,
    never invent a reference).

-   Large tasks are decomposed: phases are generated first, then tasks per phase, and each requirement is checked against its own
    acceptance criteria.

-   Only authorized project context is placed in the prompt. Passwords, tokens and keys are never included (SRS technical rule 8).

-   Retrieved web text and repository content are treated as untrusted data. The prompt marks them as quoted material and
    instructs the model not to follow instructions found inside them.

-   Prompt templates are versioned. The template version is stored with every AI result.

-   Output is requested as JSON that matches a schema. The AI service validates it, retries once with a corrective message if it
    fails, and then returns an error.

-   Language model training. Llama 3.2 3B is not trained or fine-tuned in this project. Only the Scikit-learn models are trained.

-   Pipeline. Each model is a Scikit-learn Pipeline (preprocessing plus estimator) so that the same transformations apply in
    training and in service.

-   Evaluation. Classifiers use stratified k-fold cross-validation with accuracy, macro F1 and a confusion matrix; M4 prioritizes
    recall for the High risk class. The regressor uses mean absolute error, root mean squared error and R squared. A held-out test
    set is kept untouched.

-   Starting targets. Suggested initial targets are a macro F1 of at least 0.80 for M1, recall of at least 0.80 for the High class
    of M4, and a mean absolute error of M2 within 20 percent of the mean task effort. These targets are to be revised once
    baseline results exist.

-   Storage and versions. Trained pipelines are saved with joblib together with a version tag, training date, data description and
    metric file. The AI service loads a named version at start-up.

-   Retraining. Retraining is manual and offline, uses project metadata only (no credentials and no direct personal identifiers),
    and a new version replaces the current one only if it performs at least as well on the test set. The previous version stays
    available for rollback.

-   Fallback. If a model file is missing or its confidence is low, the service uses a rule-based default and marks the output as
    rule-based.

5.9 AI Evidence Verification

Evidence verification compares what a student submits with the acceptance criteria of a task. GitHub repositories are the primary
evidence. The AI checks accessibility, gathers repository data, evaluates each criterion and produces a report. It does not run
the submitted code.

Figure 3: Evidence verification pipeline

5.9.1 Data Collected from GitHub

-   Repository metadata: whether the repository exists and is reachable, its default branch and primary languages.

-   File tree and the content of files whose paths or names match the task (selected by path rules and by retrieval over
    repository files).

-   README and documentation files.

-   Commit and pull-request data, including any commit or pull-request links the student supplied, and commit activity in the
    period of the task.

-   Supporting evidence supplied with the submission, such as screenshots and documents.

The GitHub REST API is used for this. Unauthenticated requests have a low hourly rate limit, so the backend uses a server-side
access token for higher limits. The token is held in the server configuration, is never placed in a prompt and is never shown to
users. A private repository can be read only if the student has granted access in a way the platform supports; otherwise it counts
as inaccessible.

06. Technical Architecture

6.1 Purpose and Scope

This section describes how the AI Project Supervisor is built: the MERN-based web architecture, the Python AI and machine learning
service, the integration with Ollama, the database design, the API design, security and deployment. It follows the technology

6.2 Architecture Overview

The system uses a layered architecture with a separate AI service. The React application talks only to the Node.js and Express
API. The API enforces authentication, role-based access and project-level access, owns all business rules and is the only
component that writes business data. It calls an internal Python AI service for anything that needs the language model, RAG or
machine learning. The AI service calls Ollama, which hosts the language model locally.

6.9 Security Architecture

Table 34: Security controls

  ---------------------------------------------------------------------------------------------------------------------------------
  Area                             Control
  -------------------------------- ------------------------------------------------------------------------------------------------
  Authentication                   Email and password login; short-lived access token and longer-lived refresh token (lifetimes
                                   configurable); every request re-checks that the account is still active.

  Password storage                 Passwords stored only as salted hashes using a modern password hashing algorithm.

  Role-based access                Backend middleware checks the account role for every protected endpoint. The frontend only
                                   mirrors the rules.

  Project-level access             Membership, project-level role and supervisor assignment are checked in addition to the account
                                   role. Users and AI jobs cannot reach other projects.

  Super Admin protection           Only the Super Admin can change roles, promote or demote Sub Admins; no Sub Admin action can
                                   modify the Super Admin account; all changes are logged.

  Input validation                 Schema validation on every request; output encoding in the interface; protection against NoSQL
                                   injection by rejecting operator keys in user input.

  Rate limiting                    Per-IP and per-user limits, stricter on login, AI and certificate-verification endpoints.

  Transport                        HTTPS for all external traffic; internal services bound to localhost or a private network.

  Secrets                          Keys, tokens and connection strings live in environment configuration, not in source control and
                                   not in prompts.

  AI-specific                      Secret filter before prompts; untrusted-content handling for retrieved text and repository
                                   files; schema-validated output; AI service reachable only from the API.

  File uploads                     Allowed types and size limits for screenshots and documents; files stored outside the web root
                                   and served only to authorized users.

  Audit logging                    Role changes, promotions, demotions, administrative actions, verification decisions and
                                   certificate changes are recorded with actor, time and reason.

  Privacy                          Sensitive user information is read only when necessary; certificate verification exposes only
                                   the certificate fields; the AI receives only the data its task needs.
  ---------------------------------------------------------------------------------------------------------------------------------

-   Health. The API and the AI service expose health endpoints. The AI health check also tests Ollama and the model. Sub Admins

    the API can run several instances behind the proxy, because the API is stateless apart from the database.
