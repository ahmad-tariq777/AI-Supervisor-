1. INTRODUCTION

1.1 Purpose
This Software Requirements Specification (SRS) defines the functional, non-functional, interface, data,
and artificial-intelligence requirements of Module 1: AI Project Supervisor, the core module of the
AI-Powered Platform for Project Idea Discovery, Planning, Progress Monitoring and Certification. It is
the baseline agreement between the project team, the academic supervisor, and other stakeholders on
what the system shall do and under which constraints it shall operate.
The document is intended for the following readers:
   • Developers and architects, who use it to design, implement, and integrate the web application,
     the AI service, and the database.
   • Testers and quality reviewers, who derive test cases and acceptance tests from the uniquely
     identified requirements.
   • Academic supervisors and evaluators, who use it to confirm that the proposed system addresses
     the stated problem and is feasible.
   • Platform administrators, who use it to understand the configuration, oversight, and governance
     capabilities of the system.

1.2 Scope
The AI Project Supervisor is a web-based platform that acts as a virtual supervisor for student projects.
It guides students from the discovery of a project idea, through requirement analysis, planning, team
formation, and task execution, to monitored progress, evidence-based verification of deliverables, and
the issuing of a verifiable project completion certificate. The module uses a locally hosted Small
Language Model (SLM), Retrieval-Augmented Generation (RAG) over credible external sources, and
Python-based machine learning where applicable.
The scope of this specification includes:
   • AI-powered project idea discovery, including market and problem research with references, and
     ranked idea recommendations.
   • Project analysis and planning: requirement analysis, scope and acceptance criteria, methodology
     recommendation (Agile/Scrum, Kanban, or Waterfall), timeline generation, and team formation.
   • AI-generated execution planning: phases, sprints (where applicable), tasks, and task assignment.
   • Progress monitoring, delay detection, blocker management, and corrective recommendations.
   • Deliverable submission (GitHub repositories as primary evidence) and AI-based evidence
     verification with supervisor override.
   • Project completion evaluation, certificate generation, and certificate verification.
   • Role-based access control for seven roles and the administration, oversight, and audit capabilities
     that support them.
The following are outside the scope of this version:
   • Execution or dynamic testing of submitted code (verification is static analysis of evidence).
   • Fine-tuning or retraining of the language model; Llama 3.2 3B is used as released.
   • Multilingual support, supervisor analytics dashboards, and additional evidence sources, which
     are listed as future scope in the project proposal.
   • Other modules of the wider platform.

1.3 Objectives
The system shall achieve the following objectives, taken from the project proposal and the module
specification:
   • Help students discover and validate viable project ideas supported by researched, referenced
     evidence.
   • Convert an approved idea into a realistic, structured plan with clear tasks, owners, priorities, and
     deadlines.
   • Support individual and team-based work, including invitation-based team formation and leader-
     managed task assignment.
   • Track progress continuously, detect delays and blockers early, and recommend corrective action.
   • Verify submitted deliverables against predefined acceptance criteria while keeping humans in
     control of final decisions.
   • Issue unique, verifiable completion certificates only when all mandatory completion conditions
     are met.
   • Keep the solution affordable and private by running the language model locally rather than
     through a hosted service.

     requirement that may be deferred with justification. “May” states an optional capability.
   • Requirement identifiers. Every requirement has a unique, stable identifier in the form PREFIX-
     NNN (for example FR-DIS-004). Identifiers are never reused. Business rules use the form BR-
     XXX-N.

     deferrable; Could = optional enhancement.

     module specification and user-roles documents), PI, PRP, TS, or SDD (design requirement taken
     from the System Design Document).

     model, the machine learning algorithms, or numeric performance targets), this SRS states a
     proposed value and marks it “Proposed”. Proposed values shall be confirmed during design
     review or benchmarking. They are collected in Appendix B.

2. OVERALL DESCRIPTION

2.1 Product Perspective
Students often struggle to choose a viable idea, plan realistically, and coordinate within a team, while
supervisors cannot monitor every project continuously and have no scalable way to verify that submitted
work meets requirements. The AI Project Supervisor addresses this problem by acting as a virtual
supervisor that guides, tracks, and verifies student projects from start to certified completion.
The module is the core component of a larger platform and is designed to be a self-contained web
application that can be extended by further modules. It runs on a single application server, uses a locally
hosted language model, and integrates with two kinds of external services: GitHub (project evidence)
and public scholarly and web sources (research for RAG). Figure 1 shows the five stages of the project
lifecycle that the module supports.

2.4 Operating Environment
   • Server platform: Windows or Linux application server running Node.js, Python, MongoDB, and
     Ollama (PRP, SDD 6.10).
   • Client platform: a modern desktop web browser; no client-side installation is required.
   • AI hardware (Proposed): a server able to run Llama 3.2 3B through Ollama. A minimum of 16
     GB of system memory and a multi-core CPU is proposed; a GPU is optional. The final
     specification shall be set after benchmarking on the target hardware.
   • Network: internet access from the server to GitHub and to scholarly and web sources for RAG.
     The language model itself does not require internet access at run time.

2.5 Design and Implementation Constraints, Assumptions, and Dependencies
Constraints, assumptions, and dependencies that affect the design are specified in Section 11. The most
significant ones are: the language model shall run locally through Ollama; the model is a 3-billion-
parameter model with limited reasoning capacity; research claims depend on the availability of external
sources; and AI verification is static and advisory only.

3. SYSTEM ARCHITECTURE AND TECHNOLOGY REQUIREMENTS

3.1 Architectural Overview
The system uses a layered architecture with a separate AI service. The React application communicates
only with the Node.js and Express API. The API enforces authentication, role-based access, and project-
level access, owns all business rules, and is the only component that writes business data. It calls an
internal Python AI service for all AI functions. The AI service hosts the RAG pipeline and the Scikit-
learn models and is the only component that calls Ollama. Figure 2 shows the logical architecture.

4. USER ROLES AND PERMISSIONS

4.1 Overview of Roles
The module supports seven primary roles, each with specific responsibilities and permissions (UR 3.1).
The AI Supervisor is an automated system role, not a human account; its actions are performed through
the AI services under the permissions and rules configured by the platform.

4.2 Role Responsibilities, Permissions, and Restrictions
4.2.1 Student
The primary user of the platform. Students discover project ideas, analyze requirements, create plans,
execute tasks, and obtain completion certificates.
Permissions
  • Register, log in, and manage personal profile information.
  • Start a new project; discover ideas using AI or submit an existing idea; provide preferences, skills,
    and resources.
  • View AI-generated research and recommendations; select an idea; provide and approve
    requirements and scope.
  • Provide deadlines and availability; view the recommended methodology; create individual or
    team-based projects; invite students to a team.
  • Accept or reject team invitations; view phases, sprints, tasks, and assigned tasks; update task
    progress; report blockers.
  • Submit GitHub repository links and supporting evidence; view verification reports; resubmit
    deliverables.
  • View individual progress, notifications, and completion reports; download and verify their own
    certificates.
Restrictions
  • Cannot access other students’ private project information without membership or authorization.
  • Cannot modify system-wide configurations or issue completion certificates.
  • Cannot assign tasks to other members unless designated as team leader.
  • Cannot manually mark unverified deliverables as verified.

4.2.2 Team Leader
A student responsible for coordinating a team-based project: managing members, distributing tasks,
monitoring progress, and keeping activities aligned with the execution plan.
Permissions
  • All standard student permissions.
  • Create and manage the team; invite students; view invitations and membership status; remove
    members subject to project rules and supervisor oversight.
  • View all members’ tasks; assign, reassign, and modify task priorities; propose deadline changes;
    review workload and overall progress.
  • Identify delayed tasks; review reported blockers; coordinate task dependencies; review submitted
    deliverables.
  • View AI workload recommendations; modify AI-recommended assignments; request AI-
    generated plan adjustments.

   • Coordinate completion activities and communicate progress to the supervisor.
Restrictions
  • Cannot modify platform-wide configurations, issue certificates, or override supervisor decisions.
  • Cannot manually mark AI verification results as verified.
  • Cannot access projects outside authorized membership.

4.2.3 Team Member
A student who joins an existing team after accepting an invitation and is responsible for completing
assigned tasks and contributing to deliverables.
Permissions
   • Register, log in, and manage the personal profile; view accepted team projects, members, and the
     team leader.
   • View project objectives, requirements, phases, sprints, assigned tasks, descriptions, acceptance
     criteria, priorities, and deadlines.
   • Update assigned task statuses; report blockers; submit GitHub links and upload supporting
     evidence where supported.
   • View AI verification feedback; resubmit deliverables; view personal workload and contributions;
     receive notifications; view eligible certificates.
Restrictions
  • Cannot invite or remove members, assign tasks to others, modify the project scope, or modify the
     approved timeline.
  • Cannot access another team’s private information or issue certificates.

4.2.4 Supervisor
A human academic or project supervisor who oversees assigned student projects, provides guidance,
monitors progress, and reviews the quality of deliverables.
Permissions
  • Log in to the supervisor dashboard; view assigned projects, objectives, approved requirements,
    timelines, milestones, and deadlines.
  • Monitor individual and team progress, task completion reports, overdue tasks, delays, reported
    blockers, and team workload.
  • View submitted GitHub repositories and evidence; review AI verification reports; manually

  • Approve or reject deliverables; request resubmission; provide feedback and recommendations.
  • Review AI-generated completion reports; approve or reject project completion; authorize
    certificate generation if supervisor approval is enabled by the institution; monitor project history.
Restrictions
   • Cannot manage system-wide user accounts, change platform-wide AI configuration, or modify

   • Can access only projects assigned to them or otherwise explicitly authorized.
   • Cannot change Super Admin or Sub Admin permissions.

4.2.5 Super Admin
The highest-authority role. The Super Admin has oversight access to inspect everything on the platform,
manages all platform users, and creates Sub Admins by promoting users or removes Sub Admin
privileges by demoting them.
Permissions
  • User management: view, search, and filter users and profiles; activate or deactivate accounts;
    assign and update roles; manage account access; monitor user activity.
  • Sub Admin management: promote an existing registered user to Sub Admin; demote a Sub
    Admin to a regular user role; view Sub Admins and their privileges; monitor Sub Admin activity;
    review promotion and demotion records.
  • Platform oversight (read-only): inspect all projects, teams, tasks, evidence, verification reports,
    certificate records, certificate verification activity, AI configuration and status, system logs, usage
    statistics, reports, and Sub Admin actions.
Restrictions
  • Access must be authenticated and authorized.
  • All account changes, role changes, promotions, and demotions must be logged.
  • Sensitive user information shall be accessed only when necessary for authorized administrative
     purposes.
  • The Super Admin cannot be promoted, demoted, or deactivated by a Sub Admin.

4.2.6 Sub Admin
A user promoted by the Super Admin to manage the day-to-day operation of the platform, including
projects, teams, AI configuration, system settings, certificate records, and monitoring.
Permissions
  • Projects and teams: view all projects, teams, leaders, and members; monitor statuses and
    membership; manage inappropriate or invalid project records; resolve team management issues.
  • AI configuration: manage AI system configuration, the local Ollama connection, AI service
    availability, RAG settings, and supported model settings; monitor AI errors and performance.
  • System management: manage platform-wide settings and system notifications; view logs;
    monitor database and backend health; manage certificate records and investigate certificate
    verification issues.
  • Reporting: view usage statistics; monitor students, active and completed projects, and
    completion statistics; monitor AI usage and system errors.
Restrictions
   • Access must be authenticated and authorized.
   • Cannot manage user accounts or user roles, promote users to Sub Admin, or demote other Sub
     Admins.
   • Cannot modify Super Admin permissions or accounts.
   • Administrative actions affecting project or certificate records must be logged.

4.2.7 AI Supervisor (Automated Role)
The intelligent component of the platform. It acts as a virtual supervisor and assists students, team
leaders, and human supervisors throughout the project lifecycle.
Permissions
  • Discovery: collect requirements; analyze interests, skills, and resources; research trends and
    problems; identify market gaps; generate ranked recommendations with feasibility analysis and
    references.
  • Analysis and planning: analyze ideas; identify missing requirements; ask clarification questions;
    generate scope, deliverables, and acceptance criteria; recommend methodologies; generate
    timelines, phases, sprints, tasks, priorities, deadlines, and assignment recommendations.
  • Monitoring and verification: analyze task completion, delays, and workload; identify blockers;
    generate corrective recommendations; analyze GitHub evidence against acceptance criteria;
    generate verification reports.
  • Completion: evaluate completion criteria; generate final reports; determine certificate eligibility;
    request supervisor approval where required.
Restrictions
   •   Cannot independently modify Super Admin or Sub Admin permissions.
   •   Cannot access projects without authorized context or override human supervisor decisions.
   •   Cannot treat inaccessible evidence as verified.
   •   Cannot issue certificates unless all configured completion conditions are satisfied.
   •   All AI recommendations and verification decisions must be recorded for traceability.

9. AI, MACHINE LEARNING, AND RAG REQUIREMENTS

This section specifies the intelligent functionality of the module: how the locally hosted language model
is run and used, which machine learning models support it, how RAG grounds research, and which
governance controls apply. Where the module specification fixes a choice (Ollama, Llama 3.2 3B,
Python with Scikit-learn, LangChain or LlamaIndex), it is stated as a requirement. Where a detail is left
open (algorithms, embedding model, vector store), a proposed design is given and marked Proposed.

9.1 AI Design Principles
   • Local and private. The language model runs on the platform host through Ollama; project data
     is not sent to a hosted model service.
   • Language model for language, code for exactness. The model writes, explains, and reasons in
     text. Dates, percentages, dependency checks, status changes, and permissions are computed by
     deterministic code.
   • Structured and validated output. Every AI result is requested in a fixed schema, validated, and
     rejected if invalid.
   • Grounded research. Research answers are produced only after RAG retrieval and carry the
     references of the retrieved sources.
   • Recommendations, not decisions. Humans approve baselines, plans, and completion; a
     supervisor can override verification results with a recorded reason.
   • Traceable. Every AI recommendation and verification decision is recorded for review.

9.2.2 Division of Work between AI and Deterministic Code
