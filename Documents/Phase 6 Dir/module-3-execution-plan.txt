Module 3: AI-Generated Execution Plan - Directory Structure

AI Project Supervisor (Module 1 of the larger platform) | Based on SRS v1.0 and SDD v1.0 | Draft for review

1. Module summary

  ---------------------------------------------------------------------------------------------------------------------------------
  Item                                                             Detail
  ---------------------------------------------------------------- ----------------------------------------------------------------
  Type                                                             Component 3 of 5

  Purpose                                                          Divides the approved project into phases, sprints (Agile/Scrum
                                                                   only) and tasks, recommends assignments and priorities, enforces
                                                                   task status rules and dependencies, keeps the task history, and
                                                                   applies plan adjustments.

  Principal output                                                 Phases, sprints and tasks with owners, priorities and deadlines.

  Actors                                                           Team Leader, Student, Team Member, Supervisor (view), Sub Admin
                                                                   (view), AI Supervisor

  Use cases                                                        UC-07, UC-08, UC-09

  Workflows                                                        WF-09, WF-10, WF-11, WF-18

  Requirements                                                     FR-EXE-001..022; BR-EXE-1..8; MLR (M2 effort, M3 assignment)

  MongoDB collections                                              phases, sprints, tasks, taskHistory

  API groups                                                       Execution plan; Tasks; Plan adjustment
  ---------------------------------------------------------------------------------------------------------------------------------

2. How this module fits the repository

The platform is one Express API (modular monolith), one Python AI service and one React single-page app (SDD 6.2). This module is
therefore a set of folders inside those three applications, not a separate application. Each backend module folder holds its own
routes, controller, service, validators and models (SDD 6.5).

-   Backend (Node.js + Express): backend/
-   AI service (Python + FastAPI, Ollama, Scikit-learn, RAG): ai-service/
-   Frontend (React): frontend/

7. Dependencies on other modules

-   Module 0: authentication, project context, aiGateway, notifications (assignments), audit.
-   Module 2: approved requirements baseline, approved timeline and methodology, registered team.
-   Module 4: progress, alerts and verification read tasks; a verification result moves tasks to Completed or back to In Progress
    (FR-VER-010). Module 4 must call taskStatus.js, not write status directly.

8. Notes, assumptions and open points

-   The SDD does not define where the previous plan version is stored when an adjustment is applied (FR-EXE-020 requires that it
    remains recorded). No planVersions collection exists in SDD Table 31. Proposal: mark replaced phases, sprints and tasks as
    superseded and keep them, or add a planVersions collection (to be decided).
-   Deadline changes: SRS 2.2.3 says Team Leaders modify deadlines, SRS 3.2.2 says they propose them. The design lets the Team
    Leader apply a change, recorded in task history and visible to the Supervisor; whether Supervisor approval is required is open
    (SDD Appendix A, item 2).
-   A task cannot be Completed without meeting its criteria and submission requirements (BR-EXE-7). Task completion normally
    happens through verification in Module 4 (SDD Appendix A, item 5).
-   Sprints exist only for Agile/Scrum projects; Kanban and Waterfall use their own structure (FR-EXE-004, FR-EXE-006).
-   taskHistory is append-only (FR-AUD-002).

9. Suggested build order

1.  Models; task status machine (taskStatus.js) with tests.
2.  planValidator.js (fields, cycles, dates) with tests.
3.  M2 effort model; /v1/plan/generate; planGenerator.service.js.
4.  Task assignment: M3 scoring, assignment.service.js, history.
5.  Task update endpoints and dependency gating; rollup service.
6.  Plan adjustment flow; frontend pages in the same order.
