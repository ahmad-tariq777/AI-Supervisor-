2. How this module fits the repository

The platform is one Express API (modular monolith), one Python AI service and one React single-page app (SDD 6.2). This module is
therefore a set of folders inside those three applications, not a separate application. Each backend module folder holds its own
routes, controller, service, validators and models (SDD 6.5).

-   Backend (Node.js + Express): backend/
-   AI service (Python + FastAPI, Ollama, Scikit-learn, RAG): ai-service/
-   Frontend (React): frontend/

7. Dependencies on other modules

-   Module 0: authentication, systemSettings (supervisorApprovalRequired), notifications, audit.
-   Module 3: task statuses. Module 4: verified deliverables and unresolved blockers.

8. Notes, assumptions and open points

-   Certificates are issued automatically when every condition is met (and the Supervisor approved, where enabled); Sub Admins
    manage, re-issue or revoke records (SDD Appendix A, item 3 - to be confirmed).
-   Public, no-login certificate verification is an open decision (SDD Appendix A, item 4; FR-CRT-012 is a Could). If adopted,
    that endpoint must return only certificate-level fields.
-   Eligibility is decided by rule-based code; the language model only writes report text.
-   Certificate records are retained permanently and never deleted (DBR-010, BR-CRT-6).
-   Certificate verification must not require access to the student’s private workspace (BR-CRT-7). Rate-limit this endpoint (SDD
    Table 34).

9. Suggested build order

1.  Eligibility service and completion report model, with tests.
2.  Completion evaluation endpoint, report text via AI, Supervisor approval.
3.  certificateId, integrityHash, certificate model with unique index.
4.  Transactional issuing per eligible member; notifications.
5.  PDF with QR code; download endpoint.
6.  Verification endpoint and page; record administration; frontend pages in the same order.
